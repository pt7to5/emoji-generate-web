# 物品 Emoji 风格化替换工作流设计

## 1. 项目定位与目标

本项目定位为创新型产品验证，不承担商业化、规模化和完整生产系统建设目标。验证载体是一个面向用户的 HTML 网页：用户上传照片后，系统自动识别照片中的多个普通物品并标注轮廓。用户通过点击轮廓或“上一个 / 下一个”切换目标主体，将选中的物品转换为透明底 emoji 风格图像，并可选择将其替换回原图位置。

验证版聚焦边界清楚、遮挡较少的普通物品，不支持人物、视频、多主体同时生成或复杂遮挡关系。单次任务应在 60 秒内成功完成或明确失败。

### 1.1 核心验证假设

项目只回答以下三个问题：

1. **主体选择是否可用**：系统能否识别出用户想处理的物品，用户能否快速完成选择。
2. **风格化是否成立**：系统能否在简化色块和增加柔和立体效果的同时，保留物品姿态、轮廓、主色和关键特征。
3. **回贴是否自然**：原主体移除、背景修复和新主体合成后，结果是否不存在明显残影、错位或尺寸异常。

其中“透明底 emoji 是否成立”是第一优先级验证目标；“替换回原图是否自然”是第二优先级验证目标。回贴失败不等同于核心风格化假设失败。

## 2. 产品范围

### 2.1 验证版支持

- 单张 JPG、PNG 或 WebP 图片。
- 自动识别多个普通物品，最多展示置信度最高的 5 个候选。
- 点击轮廓或使用“上一个 / 下一个”切换主体。
- 展示主体透明底提取预览。
- 用户可重新框选目标区域并触发一次新的主体分割。
- 一次选择并替换一个主体。
- 固定且统一的 emoji 风格。
- 单独下载透明底 emoji PNG。
- 下载与原图尺寸一致的替换结果 PNG。
- 展示主体提取、emoji 生成、背景修复和回贴合成的中间结果，便于定位失败阶段。

### 2.2 验证版不支持

- 人物、人脸、宠物及复杂场景的专项优化。
- 视频和 GIF。
- 多主体同时生成。
- 手工画笔修补蒙版。
- 复杂的前后遮挡重建。
- 用户自定义提示词和无限风格。
- 超大图片的原始分辨率推理。
- 登录、账户、付费和权益系统。
- 批量处理和高并发保障。
- 跨设备任务恢复和长期文件存储。
- 复杂的自动候选排序与多轮自动重试。

## 3. 整体架构

系统采用前后端分离架构：

```text
HTML 前端
  │ 上传、选择主体、展示进度、结果对比、下载
  ▼
业务后端 API
  ├── 图片存储与任务管理
  ├── 主体检测与实例分割
  ├── 主体特征分析与 emoji 重绘
  ├── 程序化立体效果处理
  ├── 原背景修复
  └── 几何对齐与图像合成
```

验证版采用“检测与分割—风格化—修复与合成”的可控管线，而不是让单个生成模型直接修改整张图片。各阶段输出可独立验证、缓存和重试。

## 4. 页面设计

### 4.1 首页

首页只承担产品说明和入口功能：

- 产品标题和一句话说明。
- 一组“原图 → emoji 替换图”效果示例。
- “开始创作”按钮。
- 点击按钮进入图像编辑页。

### 4.2 图像编辑页

编辑页使用单页分阶段状态，并允许查看各阶段中间结果：

1. **上传**：支持点击或拖拽上传，并展示格式、大小和分辨率限制。
2. **识别**：上传后自动检测，原图上叠加候选主体轮廓。
3. **选择**：用户点击轮廓或使用切换按钮选择主体；选中轮廓高亮，并显示透明底提取预览。蒙版明显错误时，用户可重新框选目标区域。
4. **生成**：用户点击“生成 Emoji”，页面依次显示“提取主体、设计 Emoji、修复背景、合成图片”等真实阶段。
5. **结果**：支持原图与结果图对比，并分别提供“下载透明 Emoji”“下载替换结果”“重新生成”和“选择其他主体”。

同一时刻只突出一个主要操作：

```text
上传图片 → 选择主体 → 生成透明 Emoji → 可选回贴 → 查看和下载
```

用户切换主体时复用已经得到的检测和分割结果，不重新识别整张图片。

## 5. 后端模块

| 模块 | 职责 | 主要输出 |
|---|---|---|
| API 网关 | 校验请求、创建任务、返回状态 | 图片 ID、任务 ID、错误码 |
| 图片预处理 | 修正方向、移除元数据、重新编码、生成推理副本 | 原图、推理图 |
| 主体检测 | 定位多个普通物品 | 类别、置信度、边界框 |
| 实例分割 | 计算每个候选物品的像素级边界 | 蒙版、多边形轮廓 |
| 主体提取 | 根据蒙版得到透明底主体 | RGBA 主体图 |
| 特征分析 | 提取类别、姿态、主色、组成部分和辨识特征 | 结构化特征描述 |
| Emoji 重绘 | 简化轮廓与色块，同时保持姿态和关键要素 | 基础透明底风格图 |
| 视觉效果处理 | 添加内阴影、高光、渐变、阴影和局部模糊 | 最终透明底 emoji |
| 背景修复 | 删除原主体并补全被遮挡背景 | 无主体背景图 |
| 图像合成 | 恢复尺寸、位置、角度、边缘与局部明暗 | 最终结果图 |
| 任务管理 | 异步执行、缓存、取消、单次重试、超时和进度 | 阶段状态 |
| 文件存储 | 临时保存原图、中间文件和结果 | 短期签名地址 |

## 6. 数据流

### 6.1 上传与识别

```text
上传图片
→ 校验格式、文件大小和像素尺寸
→ 移除 EXIF 并重新编码
→ 保存原图并生成低分辨率推理图
→ 检测候选物品
→ 并行生成候选蒙版
→ 返回候选主体列表和轮廓
```

候选主体数据示例：

```json
{
  "imageId": "img_xxx",
  "width": 1920,
  "height": 1080,
  "objects": [
    {
      "objectId": "obj_01",
      "label": "cup",
      "confidence": 0.94,
      "bbox": [420, 260, 780, 850],
      "maskUrl": "/temporary/masks/obj_01.png"
    }
  ]
}
```

### 6.2 主体选择

```text
点击轮廓或切换候选项
→ 前端确定 objectId
→ 展示该主体的轮廓和透明底提取预览
→ 用户确认生成
```

### 6.3 生成与替换

```text
读取 objectId 对应的主体和蒙版
→ 分析类别、姿态、朝向、色彩和关键组成部分
→ 简化轮廓和色块
→ 生成基础 emoji 图层
→ 程序化添加内阴影、高光、渐变和模糊
→ 自动检查轮廓、方向和关键特征
→ 修复原图中的主体区域
→ 将 emoji 对齐并合成到原位置
→ 保存结果并返回下载地址
```

验证版默认只生成一个候选，避免自动选优掩盖真实模型能力和增加不必要的成本。系统记录轮廓相似度、主色一致性、朝向、主体完整度和透明背景质量，但最终质量以人工评测为准。结构明显错误时允许用户手动触发一次重新生成。

## 7. Emoji 风格规范

目标不是写实 3D 图像，而是“轮廓简化 + 少量色块 + 柔和立体效果”。

### 7.1 结构保持

- 保持原主体姿态、朝向、长宽比例和主要轮廓。
- 识别并保留 1～5 个关键组成部分。
- 保留主色、辅助色和具有辨识度的图案。
- 不新增原主体中不存在的重要结构。
- 不为了圆润效果删除决定物品身份的基本要素。

例如，杯子应保留杯身、杯口和杯把；鞋子应保留鞋底、鞋面及具有辨识度的鞋带或装饰结构。

### 7.2 色块简化

- 将照片纹理归纳为约 3～8 个主要色块。
- 合并相近颜色，删除噪点、细碎反光和不重要纹理。
- 保留显著图案和结构分界。
- 适度圆润轮廓，但不改变主体姿态。
- 使用干净的色块边界，避免写实材质噪点。

### 7.3 立体效果顺序

1. 填充基础颜色或柔和渐变。
2. 沿轮廓内侧添加内阴影，强化体积。
3. 在统一受光方向添加柔和高光。
4. 在背光区域添加低透明度阴影。
5. 对高光和阴影图层进行局部模糊。
6. 统一颜色和边缘，形成柔软、圆润的 emoji 质感。

所有效果限制在主体蒙版内，不得污染透明背景。验证版固定高光方向、阴影强度、圆润程度和模糊范围，保证不同物品的视觉一致性。

### 7.4 实现策略

采用“AI 结构重绘 + 程序化视觉效果”的混合方式：

- AI 负责理解物品、提炼结构、简化轮廓和保留关键特征。
- 图像处理模块负责内阴影、高光、渐变、模糊和透明通道。
- 自动质量检查负责比较原主体与结果的轮廓、朝向和关键部件。

该方式能够减少完全依赖生成提示词造成的风格漂移，并允许后续通过参数化配置扩展其他 emoji 风格。

## 8. 合成策略

- 使用原蒙版质心确定新主体的中心位置。
- 使用原蒙版可见面积和主体边界确定缩放比例。
- 使用主体主轴估计旋转角度。
- 保持透明边缘，清理白边和黑边。
- 根据原位置局部亮度调整 emoji 的整体明暗。
- 添加轻微接触阴影，使主体落在原场景中。
- 默认输出与原图相同的分辨率。

若风格化结果与原轮廓差异超过验证阈值，系统标记结构偏差并展示失败原因；用户可以手动重新生成一次，避免自动重试掩盖真实成功率。

## 9. API 设计

```text
POST /api/images
上传图片并创建识别任务

GET /api/images/{imageId}/objects
获取识别进度、候选主体及其轮廓

POST /api/images/{imageId}/objects/refine
根据用户重新框选的区域生成新的主体蒙版

POST /api/generations
提交 imageId 和 objectId，创建透明 emoji 生成任务

GET /api/generations/{generationId}
获取任务阶段、结果地址或错误信息

POST /api/compositions
将已生成的透明 emoji 替换回原图

POST /api/generations/{generationId}/cancel
取消尚未完成的任务
```

下载通过短期有效的签名地址完成，不暴露服务器文件路径和存储凭据。

## 10. 性能与验证记录

| 阶段 | 目标时间 |
|---|---:|
| 上传与预处理 | 1～5 秒 |
| 检测与分割 | 2～8 秒 |
| Emoji 重绘与效果处理 | 10～30 秒 |
| 背景修复 | 3～12 秒 |
| 合成与保存 | 1～3 秒 |
| 总目标 | 17～58 秒 |

60 秒是用户端总等待时间目标，包含上传、排队、模型冷启动、推理和文件保存。验证时分别记录 P50、P95 和最大耗时，不能只记录平均值。

任务达到 60 秒时应终止尚未开始的步骤，保留已经成功生成的中间产物。例如，透明 emoji 已生成但背景修复超时，用户仍可下载透明 emoji。失败任务不从头自动重跑，用户可以从失败阶段手动重试。

检测、分割和特征分析结果按图片与主体缓存，切换主体时只重新执行必要步骤。验证版不承诺高并发服务能力，但需要记录排队时间和模型处理时间，以区分产品问题与基础设施问题。

## 11. 异常与降级

| 异常 | 处理方式 |
|---|---|
| 未识别到有效物品 | 建议用户更换边界清楚、光线充足的照片 |
| 候选物品过多 | 仅展示置信度最高的前 5 个 |
| 蒙版质量不足 | 用户重新框选目标区域并触发一次新的分割 |
| 主体严重遮挡 | 标记“不建议生成”，但允许用户尝试 |
| 透明背景失败 | 使用后处理模块重新抠图 |
| 背景修复失败 | 保留透明 emoji，允许用户扩张修复区域后手动重试一次 |
| Emoji 结构偏差过大 | 展示失败原因并允许用户手动重新生成一次 |
| 模型服务异常 | 保留任务上下文并允许直接重试 |
| 任务达到 60 秒 | 停止后续步骤，保留并返回已经完成的中间产物 |
| 页面刷新 | 验证版不保证恢复；刷新前进行明确提示 |
| 用户取消 | 停止尚未开始的模型步骤并清理临时任务 |

## 12. 数据与安全

- 上传前明确提示图片将被发送到服务器处理。
- 限制文件类型、文件体积、像素尺寸和请求频率。
- 重新编码上传文件，防止文件类型伪装。
- 删除 EXIF 定位等隐私元数据。
- 原图、中间结果和结果图默认在 24 小时后自动删除。
- 文件使用随机 ID，访问链接短期有效。
- 未经明确授权，不使用用户图片训练模型。
- 日志只记录任务状态、耗时和错误码，不记录图片内容。
- 所有模型密钥只保存在后端，不进入 HTML 或浏览器请求。

## 13. 验证方法与决策门槛

### 13.1 测试样本

使用 30～50 张覆盖不同背景、光线、尺寸和物品类别的代表性图片。测试集应事先固定，不能只展示效果较好的案例。每张图片记录主体类型、遮挡程度、背景复杂度和失败阶段。

### 13.2 主体选择验证

- 80% 以上测试图片能够识别并选中预期目标主体。
- 70% 以上初始蒙版无需重新框选即可进入风格化阶段。
- 用户从识别完成到确认主体的中位时间不超过 10 秒。
- 重新框选后仍无法得到可用蒙版的样本，应记录为分割失败。

### 13.3 Emoji 风格化验证

- 70% 以上结果能被评测者识别为原主体。
- 70% 以上结果被评测者判断为符合目标 emoji 风格。
- 60% 以上结果无需重新生成即可接受。
- 结果保持正确类别、基本姿态和朝向。
- 每个结果至少保留两个预先标注的关键外观特征。
- 色块数量显著少于原始主体，并且无明显写实纹理噪点。
- 高光和阴影柔和，无明显硬边、脏边或矩形背景。
- 输出主体边缘干净，背景 Alpha 透明。
- 不同物品具有一致的高光方向、阴影强度和圆润程度。

“像原主体”和“符合 emoji 风格”由至少 3 名评测者分别打分。关键特征在生成前由项目成员针对每个测试主体预先标注，避免生成后调整评判标准。

### 13.4 回贴验证

- 70% 以上结果不存在明显原主体残影或背景破损。
- 80% 以上结果的位置、尺寸和朝向基本正确。
- 非选中区域不出现可见变化。
- 下载文件可以正常打开，画布尺寸与原图一致。

### 13.5 性能验证

- 记录每个阶段的成功率、失败原因、P50、P95 和最大耗时。
- 以用户端端到端时间为准，目标是 95% 的任务在 60 秒内成功结束或明确失败。
- 回贴阶段失败或超时，不影响用户下载已经成功生成的透明 emoji。

### 13.6 继续或停止条件

满足以下条件时，可以进入下一阶段产品化设计：

1. 主体选择、emoji 风格化和 60 秒完成率均达到上述门槛。
2. 主要失败集中在可限定的素材类型，而不是随机发生。
3. 评测者能够稳定识别原主体，并认可风格的一致性。

出现以下任一情况时，应暂停扩展功能并调整技术路线：

1. 原主体可识别率低于 70%。
2. 无需重新生成的可接受结果低于 60%。
3. 大量失败无法定位到分割、重绘、效果处理、背景修复或合成中的具体阶段。

## 14. 验证交付物

验证结束时必须形成：

1. 可重复运行的端到端 HTML 原型。
2. 固定测试集的原图、蒙版、透明 emoji、背景修复图和最终合成图。
3. 各阶段成功率、失败原因、P50/P95 耗时和人工评分报告。
4. 用户对“透明 emoji”和“替换回原图”两种输出形态的偏好记录。
5. 是否继续产品化，以及优先改进哪个模块的结论。

## 15. 后续扩展

验证通过后，按以下顺序扩展：

1. 增加简单宠物和人物主体。
2. 提供蒙版手工修补能力。
3. 支持多主体连续替换和编辑历史。
4. 引入深度与遮挡关系，改善复杂场景合成。
5. 增加经过约束的风格预设，而不是开放式提示词。
