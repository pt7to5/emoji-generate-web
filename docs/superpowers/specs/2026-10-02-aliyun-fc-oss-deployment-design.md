# Emoji 图片工作流：阿里云函数计算 + OSS 部署设计

## 1. 目标

将当前本地 React + FastAPI 图片工作流部署为可公开访问的 MVP，主要服务中国大陆用户，预计不超过 100 人。部署应满足：

- API 密钥不进入浏览器或代码仓库。
- 单次生成原则上在 60 秒内完成。
- 无请求时尽量不产生计算费用。
- 后续可以独立修改、发布和回滚前端与后端。
- 用户上传和生成图片自动过期，不作为永久相册保存。

## 2. 技术架构

### 前端

- React、TypeScript、Vite。
- 构建产物部署到阿里云 OSS 静态网站托管。
- 浏览器只访问公开前端和后端 API，不持有百度或百炼密钥。

### 后端

- Python、FastAPI、Uvicorn。
- 使用阿里云函数计算 FC 自定义容器运行。
- 容器包含 Pillow、OpenCV、PyTorch、Ultralytics 和 MobileSAM 模型。
- 通过环境变量读取百度、阿里百炼和 OSS 配置。
- 初始规格：2 vCPU、4 GB 内存、120 秒超时、单实例并发 1、最小实例数 0。

### 文件存储

- OSS 使用私有 Bucket。
- 原图、主体蒙版、透明 Emoji 和最终合成图均存入 OSS。
- 后端返回短期签名 URL，不公开 Bucket 写权限。
- 设置生命周期规则，默认 24 小时自动删除任务文件。
- FC 的 `/tmp` 只用于一次请求内的临时计算，不能作为持久存储。

## 3. 请求流程

1. 前端向 FastAPI 请求上传授权或直接上传图片。
2. 后端为任务生成随机 `imageId`，文件写入 OSS 对应前缀。
3. 用户涂抹后，后端下载任务原图到 `/tmp`，MobileSAM 完成分割。
4. 蒙版和主体预览上传 OSS，前端通过签名 URL 展示。
5. 用户点击生成后，后端调用阿里百炼生成风格化图，并调用百度抠图。
6. 后端完成颜色一致性处理和合成，将结果上传 OSS。
7. 前端获得结果 URL，支持预览、撤回和下载。

第一版继续采用同步请求，不引入消息队列。若实际 P95 请求时间超过 55 秒，再升级为异步任务和轮询状态。

## 4. 更新与发布

### 后端更新

后端可以持续修改。每次更新流程为：

1. 修改 Python 代码、提示词、依赖或模型。
2. 运行测试并构建新的 Docker 镜像。
3. 使用不可变版本号标记镜像，例如 Git 提交号或日期编号。
4. 推送镜像到阿里云容器镜像服务 ACR。
5. 在 FC 创建并发布新版本。
6. 先将少量流量切到新版本，健康检查通过后再切换全部流量。
7. 出现异常时，把流量切回上一个 FC 版本，不重新构建旧代码。

前后端独立发布。修改后端不要求重新部署前端，除非 API 请求或响应结构发生变化。

### 前端更新

1. 修改 React 页面。
2. 执行类型检查、测试和生产构建。
3. 将新的 `dist` 上传 OSS。
4. 使用带哈希的 JS/CSS 文件名，避免浏览器加载旧资源。
5. 若启用 CDN，更新后刷新 `index.html` 缓存。

### API兼容策略

- 当前接口统一保留在 `/api` 下。
- 不兼容变更新增 `/api/v2`，不直接破坏已上线前端。
- 响应字段只增加不删除；废弃字段至少保留一个发布周期。
- 前端通过环境变量配置 API 根地址，不把地址散落在组件代码中。

## 5. 稳定性

- FC 配置存活检查和第三方服务连通性检查。
- 百度、百炼请求设置明确超时，只对网络错误和 5xx 做有限重试。
- 每个请求带任务 ID，日志中不得记录完整图片、密钥或签名 URL。
- 限制上传格式、像素、文件大小和单用户请求频率。
- 同一实例并发初始设为 1，避免 MobileSAM 并发推理造成内存峰值。
- 监控生成成功率、分割成功率、P50/P95 耗时、第三方 4xx/5xx 和 FC 内存峰值。
- 若冷启动导致超时，优先配置工作时段预热；确认有稳定流量后再设置最小实例数 1。

## 6. 安全与隐私

- 所有密钥只保存在 FC 加密环境变量或阿里云密钥管理服务中。
- OSS Bucket 禁止公共写入，上传和下载使用短期签名 URL。
- CORS 只允许正式前端域名和必要的本地开发地址。
- 图片默认保留 24 小时；页面明确告知用户图片会发送给百度和阿里百炼处理。
- 限制单个 IP 或匿名会话的请求速率，防止 API 额度被滥用。
- 正式使用中国内地区域和自定义域名前完成 ICP 备案及相关合规配置。

## 7. 成本控制

- FC 最小实例数从 0 开始，无请求时释放实例。
- OSS 使用生命周期自动删除文件，避免存储持续增长。
- 前端静态文件长期缓存，减少 OSS 流量和请求数。
- 记录每次百度、百炼调用次数和失败原因，避免失败请求无限重试。
- 自动一致性重试最多一次，防止单次操作失控消耗额度。

## 8. 实施顺序

1. 将本地文件接口抽象为统一存储接口，支持本地磁盘与 OSS 两种实现。
2. 为后端创建 Dockerfile，并验证 MobileSAM 在 2 vCPU、4 GB 内存下的冷启动和推理时间。
3. 将 FastAPI 部署到 FC 测试环境，配置密钥和健康检查。
4. 将前端 API 地址改为构建环境变量，并部署到 OSS 测试站点。
5. 完成上传、涂抹分割、生成、合成、撤回和下载的端到端测试。
6. 配置 OSS 生命周期、CORS、访问控制、日志和告警。
7. 小范围邀请测试；根据耗时决定是否预热或替换为 ONNX Runtime。

## 9. 验收标准

- 用户可通过公开 HTTPS 地址完成完整流程。
- 浏览器中不存在百度、百炼或 OSS 长期密钥。
- 任务文件在设定时间后自动删除。
- 新后端版本可以灰度发布并在失败时回滚。
- 单用户正常流程不因实例重启丢失任务文件。
- 主要接口错误能区分网络、额度、输入、分割和生成失败。
- 10–20 张现有测试图片完成回归测试并记录成功率与耗时。
